# BIM Pack Web · GLB 处理与查看

纯前端（浏览器内运行）的 GLB 处理工具：**拖入模型 → 体检 → 压缩 → 3D 预览 → 层级树 → 下载**。
不依赖 Node 服务、不上传文件，所有计算都在本地浏览器完成。

打开的界面就是拖放区——不自动加载任何模型。

---

## 怎么跑

```bash
cd bimpack/web
npm install          # 只需第一次
npm run dev          # → http://localhost:5173
```

构建成静态站点（可丢到任意静态托管：GitHub Pages / OSS / COS / Nginx）：

```bash
npm run build        # 产物在 dist/，用相对路径，放子目录也能跑
npm run preview      # 本地预览构建产物
```

> `dist/` 是纯静态文件，没有任何服务端依赖。但**不能直接双击 index.html**——
> ES module 和 wasm 在 `file://` 下会被浏览器的同源策略拦住，必须走一个静态服务器。

---

## 能干什么

| 能力 | 说明 |
|---|---|
| **直接查看** | 拖入 `.glb` 立刻渲染，不做任何几何改动（只修非法的 `asset.version`） |
| **压缩处理** | reorder + meshopt FILTER 编码，实测 208 MB → 113 MB（−45.7%） |
| **层级树** | 按 BIM 属性合成**规范层级**：专业 → 系统 → 类别 → 类型 → 构件（源文件是平铺的，见下），另可切 专业›设备分类（两级；智能化、管综各自单独成一级，管综内按专业方向 › 类别细分）/ 系统›类别 / 类别›类型 / 原始结构，懒加载 + 名称搜索 |
| **BIM 属性** | 点构件看全部 `extras` 用户属性（实测单构件 71 条） |
| **批处理渲染** | 12,209 个独立 Mesh → **29 个 draw call**（按材质分组） |
| **校验闸门** | 压缩后跑 19 项比对，任何一项不过都不会让你下载 |
| **拒绝重复压缩** | 已经压到极限的文件（≤8 字节/顶点）不再让压，按钮直接变「已压缩」 |
| **下载** | 处理后的 `.glb`，或仅修过版本的原始文件 |

### 交互

- 左键拖 = 旋转，右键拖 = 平移，滚轮 = 缩放
- **单击构件 = 只高亮 + 出属性，相机不动**（在模型上点、在树上点都一样）
- **双击构件 / 树节点 = 相机平滑飞过去**（想看清某个构件时用），**再双击同一目标就原路飞回**
- 聚焦后按 `Esc`、或双击空白处，同样回到初始视角；「适应视图」也照旧可用
  （返回点是**第一次**聚焦前的视角，连跳多个构件也不会丢）
- 聚焦状态下**滚轮照常能拉远到全景**：拉远上限按整模型算（不是按那个小构件），
  近/远裁面随观察距离每帧自适应，所以不会出现「滚轮往下拉不动 / 一拉整栋楼被切掉」
- 树上的「▤」是分组、「◆」是构件；点分组名会展开，右侧数字是该组构件数
- 顶栏「层级树 / 属性」按钮、面板右上角 `×`、快捷键 `1` / `2` = 显示或收起面板
- 「适应视图」（快捷键 `F`）= 回到能看全整个模型的角度；「俯视」= 正上方看平面；「网格」= 地面参考网格
- 搜索框输名称 = 全树过滤，点结果直接选中
- `Esc` = 退出聚焦（回到初始视角）；没有聚焦时 = 取消选中

> 面板收起/展开、窗口缩放时，只要**你没手动转过视角**，相机就会自动重新取景，
> 保证模型始终完整显示（这是 V1 里"模型装不下"的根因之一，见下一节）。

### 为什么压过的文件不让再压

不是保守，是数学。Draco / meshopt 的量化把坐标存成 16 bit 整型，浏览器端的
meshopt FILTER **不做量化**、只做 delta + 熵编码，读进来坐标又变回 float32。
所以「量化解回浮点再压一次」必然膨胀 —— 实测一份 63.63 MB 的 Draco 产物被压成了 **115.34 MB**。

判据不是「有没有 Draco 扩展」：**3ds Max 的原始导出本身就带 Draco**，但用的是低压缩设置
（25.46 字节/顶点），重压能到 4.5，这正是主流程。所以看的是每顶点字节数：

| 文件 | 字节/顶点 | 按此按钮 |
|---|---|---|
| 3ds Max 原始导出 | 25.46 | ✅ 可压 |
| 本工具 meshopt 产物 | ≈11.3 | ⛔ 已压缩（同算法无收益） |
| Draco edgebreaker 产物 | 4.54 | ⛔ 已压缩（已到极限） |

低于 **8 字节/顶点** 就判定为「压够了」。要更小只能回到原始导出，用**本地 Draco 工具**
重压（那个工具在本机 `local-tools/draco-tool/`，**不在本仓库**），它做量化，
实测 208 MB → 63 MB（−69.6%），比浏览器版多压一半。

### 为什么有的模型会报 `Cannot read properties of null (reading 'length')`

这不是模型的几何坏了，是导出的 JSON 里有**规范不允许的 null**。最常见三处：

- 图元上的 `"targets": null`（形变目标）
- 节点 / mesh 上的 `"weights": null`（形变权重）
- mesh 里没有 `primitives`

three.js 的 `GLTFLoader` 在这些地方用 `!== undefined` 判空，null 会被当成「有值」，
接着直接 `null.length` —— 报错就长这样，且完全看不出是哪个字段。

所以进解析器之前会做一次字节级清洗（`core/glb.js` 的 `prepareGLB`）：

1. 把 `extras` 之外的 null **删掉**（删掉 = 回落到规范默认值；`extras` 是 BIM 属性，里面的 null 原样保留）
2. 引用型数组（场景根节点、children、joints、primitives、targets）里的 null 元素剔除
   —— 注意只动这类「纯引用列表」，像 `nodes` / `meshes` / `accessors` 这种按**下标**被引用的数组绝不能删元素
3. 没有 `primitives` 的 mesh 补成 `[]`，退化成一个空 Group 被批处理跳过 —— 一个坏图元不该让整层楼打不开

回归测试：`node test/sanitize.mjs`（9 项断言，含「extras 里的 null 必须保留」）。

### 为什么层级树是"合成"的

3ds Max 的 glTF 导出器把这层信息丢掉了：本例 208 MB 文件里 **12,244 个节点全在根上、
零子节点、最大深度 0**。照原样铺就是一条一万多行的平列表——既看不懂也没法用。

所以按 `extras` 里的 BIM 属性合成层级。**主线只有一套**：专业 → 系统 → 类别 → 类型 → 构件；
下拉里另外几档是同一批构件的**换轴视图**，不是并行的第二棵树 ——
构件不会在多棵树里重复出现，分组计数之和永远等于构件总数。

#### 为什么用「专业」当总层

模型里其实有两套**正交**的轴：

- **构件分类轴**：类别 → 族 → 类型 → 构件（IFC 的 `IfcTypeObject` 体系，即 Revit 的 Category / Family / Type）
- **系统轴**：系统 → 构件（IFC 的 `IfcDistributionSystem` + `IfcRelAssignsToGroup`）

一根排烟风管，既「是一种风管」，又「属于某个排烟系统」。要合成一棵树，必须选一条当主干、
把另一条降级。按机电出图与验收的惯用口径，顺序是**先分专业、再分系统、最后才是构件类别**，
于是主干定为五级：

| 层级 | 取值来源 | 例子 |
|---|---|---|
| ① 专业 | 由系统字段 / 类别 / 族推导（`src/viewer/discipline.js`） | 暖通空调 / 给排水 / 消防 / 电气 / 安防 / 燃气 / 建筑 / 结构（安防即 ELV，见下） |
| ② 系统 | `系统缩写` 优先，没有才解析 `系统名称` | `PY` `CHW` `SP` `AL` |
| ③ 类别 | `Category Name` | 风管 / 管道 / 电缆桥架 |
| ④ 类型 | `Type Name` | 镀锌铁皮 / 无缝钢管 |
| ⑤ 构件 | 网格实例 | `排烟风管 PY 5` |

**依据**（口径来源，不是自创）：

- GB/T 51269-2017《建筑信息模型分类和编码标准》：按专业—系统—构件类型分层编码
- GB/T 51301-2018《建筑信息模型设计交付标准》：模型按专业与系统组织，系统应可追溯
- IFC4（ISO 16739-1）`IfcDistributionSystem.PredefinedType`：AIRCONDITIONING / VENTILATION /
  DOMESTICCOLDWATER / SANITARY / FIREPROTECTION / ELECTRICAL / COMMUNICATIONS
- 各专业验收规范的划分：GB 50242（给排水及采暖）、GB 50243（通风与空调）、GB 50303（建筑电气）、
  GB 50974（消防给水及消火栓）、GB 51251（防烟排烟）、GB 50116（火灾自动报警）、
  GB 51309（消防应急照明）、GB 55037（建筑防火通用规范）

#### 原来的多套层级怎么合并

| 原分组 | 现在的去处 |
|---|---|
| 类别 → 类型 | 主干第 ③④ 层；同时保留为「类别›类型」换轴视图 |
| 系统（缩写） → 类别 | 主干第 ②③ 层（上方新增 ① 专业）；同时保留为「系统›类别」换轴视图 |
| 系统（缩写） → 类别 → 类型 | **下架**：展开类别就是类型，「系统›类别」已经够用，单列一档是同一件事多一个入口 |
| 系统›专业›设备 | **下架**（2026-11）：先系统后专业要绕一圈，找设备不如「专业›设备分类」直接；管综单独成桶的做法已并入两级视图（智能化同样单独成一级） |
| 族 → 类型 | **下架**：族是类型的容器，与类型语义重叠；族在属性面板里看 |
| 标高 → 类别 | **下架**：楼层是空间维度，与系统轴正交（一根立管跨 31 层，塞进树只能二选一）；计划改成筛选器 |
| 原始结构 | 保留：兜底视图，源文件真有层级时才用得上（平的源文件会退化成平列表） |

下拉共五档，**平铺不分组**（这几条还分两级反而多占一行、还让人以为是两套并行的树）：

| 档位 | 层级 |
|---|---|
| 专业›系统›类别›类型 | 规范层级（默认，主干五级到构件） |
| 专业›设备分类 | **两级视图**：专业 → 设备分类（风机 / 风机盘管 / 水泵 / 配电柜…），另有「智能化」「管综」两个一级归类；管综内部再分「专业方向 → 类别」，见下节 |
| 系统›类别 | 换轴看系统：缩写定类别，编号不参与 |
| 类别›类型 | 换轴看构件：Revit 类别 → 类型，与专业无关 |
| 原始结构 | 文件里的节点层级原样铺开 |

**空层折叠**：整层只有一个取值时自动折叠 —— 建筑结构模型没有系统字段，就不会多出一层全是
`其他分类` 的假层级；单个构件缺系统 / 族 / 类别 / 类型时也不给它造空节点，直接挂到上一级
（深度按实际经过的层数算）—— 手工添加的非 BIM 模型因此是「专业 → 系统 → 构件」，不会多出两层空类别。

#### 两级视图：专业 › 设备分类

这一档只回答两个问题：「这是哪个专业的」「这专业里有哪些设备」。**不分系统**，也不分
类别 / 类型 —— 第二层直接是设备分类，所以「暖通空调」底下就是它那一批设备，一眼能数出各有多少件。

第 1 层除了各专业，还有两个**从专业里拎出来的归类**（都不是专业，各占一级）：

- **智能化**：名称里带「智能 / 智慧 / 智控 / 智联」的设备。这些设备横跨电气与安防
  （智能照明、智慧安防、智能配电箱…），散在各专业下要翻好几处才数得清，所以收成一级，
  排在所有专业之后、管综之前，展开后按系统名分组。
- **管综**：管道 / 风管 / 桥架 / 支吊架等「线」类构件，不是设备，排最后。
  它内部**先按专业方向拆**（暖通空调 / 给排水 / 消防 / 电气 / 安防…，与第 1 层同名同色），
  再按 Revit 类别细分（风管 / 管道 / 电缆桥架…）—— 三级，见下面示例。

```
暖通空调                 ← 专业（第 1 层，按业务序：暖通 → 给排水 → 消防 → 电气 → 安防 → 建筑 → 结构）
├ 空调机柜          1
├ 新风机组          1
├ 风机盘管          1
└ 水泵              1
给排水
└ 水箱              1
电气                     ← 只剩常规设备，智能化已单独成一级
├ 配电柜            2
└ 其他设备          1
建筑
└ 墙                3    ← 建筑构件不并进设备分类，给 Revit 类别
智能化                   ← 名称带「智能 / 智慧」的设备全收在这里
├ 智能照明          1    ← 第二层按系统名分组，与主干视图的系统层同名
└ 智慧安防          1
管综                     ← 管综单独成一级、排最后
├ 暖通空调          2    ← 第 2 层：专业方向（与第 1 层同名同色）
│  ├ 风管            1    ← 第 3 层：Revit 类别，便于按类筛选
│  └ 管道            1
├ 给排水            1
│  └ 管道附件        1
├ 电气              1
│  └ 电缆桥架        1
└ 安防              1
   └ 其他分类        1    ← 手工模型没有 Revit 类别
```

45F 实测（8071 构件）：`管综 6764` = 暖通空调 3179 + 给排水 56 + 消防 3204 + 电气 255 + 其他分类 70；
其中「消防」展开是 风管 57 / 风管附件 32 / 风管管件 21 / 风口 8 / 管道 1558 / 管道附件 12 / 管件 1479 / 机械设备 37。

**行格式**：第 1 层每一行都带圆点 —— 专业按 `disc-XXX` 上色（暖通蓝 / 给排水绿 / 消防红 / 电气橙 /
安防紫 / 建筑深灰 / 结构浅灰）；「智能化」与「管综」不是专业，分别用淡紫点 `disc-smart`、
中性灰点 `disc-bucket` 占位，文字与各专业左缘对齐，不会看起来比人家「缩进少一格」。
「管综 › 专业方向」那几行**沿用本专业的颜色**（暖通蓝 / 给排水绿 / 消防红 / 电气橙…），
与第 1 层一眼能对上。

**字段结构**（`web/src/viewer/tree.js` 的 `GROUP_MODES.discEquip`，三个 field，第 3 个只对管综生效）：

| 层 | key | 取值 | 数据来源 |
|---|---|---|---|
| ① | `专业` | 暖通空调 / 给排水 / 消防 / 电气 / 安防 / 燃气 / 建筑 / 结构 / 其他 / 其他分类，**外加单独的「智能化」与「管综」两级** | `discipline.js`：`classifyLeaves()`（整批，含「同类别多数」兜底）+ `disciplineCode()`；设备分类为 `智能化设备` 的构件改判到「智能化」一级、为 `管综` 的改判到「管综」一级（`fix` 钩子，两级都排在专业之后） |
| ② | `设备分类` | 空调机柜 / 新风机组 / 风机盘管 / 水泵 / 水箱 / 配电柜 / 其他设备…；**「智能化」一级下按系统名显示**（智能照明 / 智慧安防，认不出系统名给「未分系统」）；**「管综」一级下是专业方向**（暖通空调 / 给排水 / 消防 / 电气 / 安防 / 其他分类）；建筑 / 结构这两支给 Revit 类别（墙 / 门 / 窗） | `equipment.js`：`equipmentKind()`（即 `resolveEquipment().kind`）；智能化设备再取**系统键** `sysKeyOfLeaf()`；管综下复用第 1 层整批算好的专业（`leaf.__disc`，含「同类别多数」兜底，口径与各专业一致）；建筑 / 结构取 `Category Name` |
| ③ | `类别`（`only`：只对管综生效） | 风管 / 风管附件 / 风管管件 / 风口 / 管道 / 管道附件 / 管件 / 电缆桥架…；没有 Revit 类别的手工模型给「其他分类」 | `Category Name`（缺失时退 `类别`） |

**智能化单独成一级 + 第二层按系统名**：

- 一级收到一起 —— 智能设备横跨电气（智能照明、智能配电箱）与安防（智慧安防摄像头、门禁），
  按专业分会散在两处；单独成一级后一眼能看到「全楼智能设备共 N 件」，
  某 45F 实测：智能化 198 件 = 智能照明 174 + 智慧安防 24。
- 二级仍分系统 —— 这个池子很宽，笼统堆成一层看不出是哪套系统，也和主干视图
  「专业 → 系统 → 类别 → 类型」的叫法对不上。所以沿用同一个系统键当标签
  （`智能照明` / `智慧安防`），两边名字一致；系统名认不出时给「未分系统」。
- **管线本体不退让**：名称带「智能」的桥架 / 管道仍归「管综」（`智能化_电缆桥架001` 在管综里），
  建筑构件同理（`智能防火门` 仍是建筑 › 门），它们不会被吸进「智能化」。

排序：一级按 `DISCIPLINES` 的 `order`（暖通 10 → 给排水 20 → 消防 30 → 电气 40 → 安防 50 →
燃气 55 → 建筑 80 → 结构 81 → 其他 90 → 其他分类 99），之后「智能化」850、「管综」900 压最后；
设备分类层按 `kindRank()` 的业务序（冷热源 → 水 → 电 → 弱电 → 智能化 → 照明 → 电梯 → 其他设备），
「管综」下这一层是专业方向、同样按 `DISCIPLINES.order`；Revit 类别没有业务序，按名称排。

**与现有模型的关联**（为什么不新增归类逻辑）：

- 叶子还是同一批：`batchModel()` 产出的 `objectToRecs`（Object3D → 构件记录），不增不减，
  所以这一档的叶子总数、各行计数与另外几档**完全一致**（回归测试里对着主干视图比过）。
- 属性还是同一份：`rec.props`（GLB 的 `extras`）。专业层与设备分类层都只是「读属性 + 归类」，
  不写回模型、不改材质、不影响压缩与下载。
- 判定规则与主干视图共用：`discipline.js` 判专业、`equipment.js` 判设备分类，
  所以同一根风管在「管综 › 暖通空调 › 风管」和「暖通空调 → 系统 → 风管」里是同一个归属，
  不会两处矛盾；「管综 › 专业」直接复用第 1 层整批判好的专业（`leaf.__disc`），没有第二套规则。
  「智能化」只是把 `智能化设备` 这一个设备分类整体提到一级，同样没有新规则。
- 与主干的差别只是**少了几层**：主干是 专业 → 系统 → 类别 → 类型，这一档把「系统」「类别 / 类型」
  都省掉，设备直接摊在专业下；「管综」这一支保留「专业 → 类别」两层，其余分支两层到构件。
  需要追溯系统或型号时切回主干即可。
- 显隐、搜索、右键菜单、3D 点选反查都走同一套节点接口（`recs` / `children`），所以取消「管综」
  一行的勾选就是「只看设备」，和别的档位行为一致。

#### 设备分类怎么判定（equipment.js）

判定顺序（`resolveEquipment()`，越靠前越权威）：

| # | 依据 | 例子 |
|---|---|---|
| ① | **建筑 / 结构专业 → 一票否决**，不并入任何设备分类（这两支按 Revit 类别展开） | `基本墙 电梯井道轻质隔墙_150`、`混凝土-矩形梁_电梯大堂` —— 名字带「电梯」也还是墙和梁 |
| ② | **建筑构件类别 → 一票否决**（墙 / 门 / 窗 / 楼板 / 楼梯 / 幕墙…） | `门 | 智能防火门` —— 带消防词、带「智能」，仍然只是门 |
| ③ | **类别本身是管线** → 归「管综」 | `电缆桥架 | CT-广播线槽`（「广播」是系统名）、`管道附件 | 压力传感器` |
| ④ | **名称带「智能 / 智慧 / 智控 / 智联」** → 「智能化设备」（见下节） | `智能照明_筒灯001`、`智慧_水泵001`、`Smart Lighting Panel` |
| ⑤ | 名称 / 类别 / 族 / 类型 里的**设备词**（从细到粗，先命中先算） | `组合式空调机组 AHU-1` → 空调机柜 |
| ⑥ | **IFC 实体**（中文名认不出时兜底） | `IfcPump` → 水泵、`IfcChiller` → 冷水机组 |
| ⑦ | **管综词** → 归「管综」 | 风管 / 管道 / 桥架 / 阀门 / 风口 / 支吊架 / 管卡 / 木托 / 弯头 |
| ⑧ | 管综类 IFC 实体 → 「管综」 | `IfcFlowSegment` / `IfcDuctSegment` / `IfcCableCarrierSegment` |
| ⑨ | 类别写着机械设备 / 专用设备 / 设备但认不出型号 → 「其他设备」 | 自定义族 + 甲型 |
| ⑩ | 其余 → 「其他设备」 | 认不出型号的构件不硬说成管道 |

前三条是**硬优先级**，压过一切设备词与「智能」字样 —— 它们各对应一次真实翻车：
「电梯井道轻质隔墙」曾被「电梯」拉进电梯设备，「广播线槽」曾被「广播」拉进设备，
「智能防火门」差一点被「智能」拉进智能化。

设备分类（内部叫「设备类型」）共 16 类，按业务顺序排（不是拼音序）：

```
冷水机组 / 空调机柜 / 新风机组 / 风机盘管 / 冷却塔 / 锅炉 / 换热器 / 风机 / 水泵 /
水箱 / 水处理设备 / 配电柜 / 弱电机柜 / 智能化设备 / 照明灯具 / 电梯设备
→ 其他设备 → 管综 → 建筑结构（大桶沉底，不挡路）
```

四个刻意的取舍：

- **建筑结构只留在「建筑结构」**。墙、梁、板、柱、门、井道不许并入任何设备类型，哪怕名字里
  带了「电梯」「机房」这类词。
- **不读「系统分类 / 系统名称」**。那说的是管线属于哪个系统（冷冻水、配电），一根冷冻水管
  也在冷冻水系统里，按系统判会把整片管道都当设备。同理，弱电专业的系统名常直接叫
  「智能化」—— 读系统名会让整层桥架、线槽全部涌进「智能化设备」。
- **词表只收两个字以上的词**。单字「泵」「柜」会把「泵房」「柜体」误伤成设备 ——
  这条是从「机械设备被划到结构」那次的单字「板」学来的。
- **「智能化」是设备口径，不是专业口径**。它回答「这台东西是不是智能设备」，
  和专业层里的「安防（ELV）」不是一回事：弱电桥架仍在「管综」，弱电机柜仍在「弱电机柜」。

> 专业名口径：`ELV` 这个专业在本项目显示为 **安防**（原叫「智能化」）。
> 原因是它下面的系统就是智慧安防，而设备类型那一层已经叫「智能化设备」——
> 树上会出现「智能化设备 > 智能化 > 智慧安防」父子同名；改成「安防」后是
> 「智能化设备 > 安防 > 智慧安防」。判定代码与关键词（智能化 / 弱电 / 网络 /
> 综合布线 / 监控 / 门禁 / 广播 / 安防）都不变，只改显示名，
> 换项目时改 `discipline.js` 里的 `ELV_LABEL` 一行即可。

#### 智能化设备：只认名字，不认系统

手工添加的非 BIM 模型没有类别 / 族 / 类型，唯一线索是「系统名_设备名+编号」的名字；
BIM 模型有完整属性，但也会按同样口径归一次。两边的判定完全共用一条规则：

```
名称（或 名称/类别/族/类型 的任意字段）里出现 → 智能化设备
  智能 · 智慧 · 智控 · 智联          （中文，子串命中）
  smart · intelligent · intelligence（英文，整词命中，不命中 smartphone）
```

| 场景 | 输入 | 结果 |
|---|---|---|
| 手工模型，设备本体 | `智能照明_筒灯001` | **智能化设备**（不再拆成「照明灯具」） |
| 手工模型，设备本体 | `智慧_水泵001` | **智能化设备**（设备词让位） |
| 手工模型，管线本体 | `智能化_电缆桥架001`、`智能电动阀`、`智慧_风口001` | **管综**（带智能也是线） |
| BIM，族里带智能 | `类别=机械设备, 族=智能配电箱` | **智能化设备** |
| BIM，类别是管线 | `类别=电缆桥架, 族=智能化桥架` | **管综** |
| BIM，建筑构件 | `类别=门, 族=智能防火门`、`类别=墙, 类型=智能化隔墙` | **建筑结构** |
| 系统名带智能 | `系统名称=智能化, 名称=筒灯001` | **照明灯具**（系统名不参与） |
| 只有单字「智」 | `智造中心_支架` | **管综**（不收单字「智」，避免「智利 / 智造」误伤） |
| 英文整词边界 | `Smart Lighting Panel` / `Smartphone rack` | 智能化设备 / 其他设备 |

优先级一句话：**建筑结构 > 管线本体 > 智能化 > 具体设备词**。

- 「智能化」压过具体设备词，是因为它是一句**显式声明**（用户说「这是智能设备」），
  而「筒灯 / 水泵」只是型号归类。若某天希望「智能配电箱」仍归配电柜，
  把 ④ 挪到 ⑤ 之后即可（一行改动，`test/smart-equip.mjs` 里锁着现在的口径）。
- 「管线本体」不退让：一根智能桥架、智能电动阀仍是管综 —— 否则「管综」这层筛选就漏了。
- 智能化设备**算真设备**（不在兜底桶里），排序在「弱电机柜」之后、「照明灯具」之前。

**当筛选用**：取消「管综」勾选 → 只剩设备（含智能化）；再取消「智能化设备」→ 只看常规机电；
悬浮提示会写明这一类是按名称里的「智能 / 智慧」归进来的。

> 早期还有一档「末端设备」，把传感器、温控器、灯具、桥架配件混在一个桶里（某 31F 模型
> 一口气装了 328 件，其中 192 件是管道上的温度/压力传感器、10 件是电缆桥架）。现已取消：
> 传感器按类别归「管综」，灯具归「照明灯具」，其余认不出型号的进「其他设备」。

**当筛选用**：每行左侧的勾选框本来就能隐藏整棵子树，取消「管综」的勾选就只剩设备；
再配合顶部的名称搜索，可以做到「只看配电柜」。悬浮提示会写明这一类是设备、管综还是非机电，
以及当前有多少件。

#### 归并冲突与特殊处理

| 冲突 | 处理 | 依据 |
|---|---|---|
| 排烟风管：设备是「风管」（暖通），系统是「排烟」（消防） | **消防优先** —— 命中排烟 / 防烟 / 喷淋 / 消火栓 / 火警等词一律归消防，不拆散进暖通或给排水 | GB 55037、GB 51251、GB 50974 要求消防独立成体系、单独验收 |
| 同类别的构件落在两个专业（「风管」在暖通与消防下各有一份） | **允许**：合并粒度是「专业 + 系统」，不是类别。两份互不干扰，叶子不重复 | — |
| 缩写跨项目含义不一（`NW` 在 A 院是凝结水、B 院是网络；`CR` 可能是冷媒或冷却水回水） | 中文语义优先、缩写只作兜底；有歧义的缩写出表（见下）；仍判断不出就用组内最常见类型名，悬浮提示写明来源 | — |
| 消防是否单列存在两种口径（有的院把消防水并入给排水） | `POLICY.fireFirst = false` 时按**实体专业**归并：排烟 → 暖通、喷淋 / 消火栓 → 给排水、火灾报警 → 电气 | 可配置，默认单列 |
| 构件无任何系统字段（建筑 / 结构） | 落到「建筑」「结构」专业；既无系统也无类别 → 「其他分类」，排在最后 | — |
| 多系统值（`CR 30,CR 18`） | 只取第一个作主系统，避免一个构件在多系统下被重复计数 | — |
| 族与类型重名 / 族跨类别 | 族不进主干（只在可选的第 ④ 层出现），避免「族」和「类别」两套近似语义打架 | — |
| 标高 | 不进主干（见上表），当前在属性面板看，后续计划做成筛选器 | — |


#### 系统归类规则：缩写定类别，编号不参与

机电模型的「系统名称」写法五花八门（`CN 5`、`CN-7`、`cn-9`、`CWP 3`、`CR 30,CR 18`…），
直接用原值分组会把同一个系统拆成一堆平行分组。规则统一为
**「系统缩写 = 类别，缩写后的编号一律忽略」**，对任何模型都用同一套解析（`systemAbbr()`）：

| 步骤 | 处理 | 例子 |
|---|---|---|
| 1 | 多系统值只取**第一个**系统条目（按 `, ， ; ； / 、 \| +` 切分） | `CR 30,CR 18` → `CR 30` → **CR** |
| 2 | 去掉括号注释 | `CN 5(备用)` → **CN** |
| 3 | 取开头字母段（字母间允许 `- _ .` 连接），遇数字/空白/中文即止 | `CN 5` `CN-5` `CN_05` `CN5` `cn 9` → 都是 **CN**；`CHW-B 12` → **CHW-B** |
| 4 | 统一大写、压缩空白 | `cwp 3` → **CWP** |
| 5 | 不以字母开头时，剔除结尾的编号段，其余保留 | `生活给水 JL 3` → **生活给水 JL** |
| 6 | 纯数字/空值没有分类意义 → 归「其他分类」 | `12 34` → **（其他分类）** |

**分类键优先用模型自带字段**：先取 `系统缩写`（如 `EAD`），没有才解析 `系统名称`（`EAD 5` → `EAD`）。
两者都不看编号，缩写后的数字一律不参与归属。

**缩写后面显示中文系统名**，按四级优先级取，前一级拿不到才退下一级：

| 优先级 | 来源 | 例子 |
|---|---|---|
| ① | 模型自带 `系统类型`（去掉缩写前缀） | `EAD-排风管` → **排风管** |
| ② | 模型自带 `系统分类` | `排风` → **排风** |
| ③ | 内置对照表 `src/viewer/system-names.js` | `CN` → **冷凝水**、`CWP` → **冷却水泵** |
| ④ | 该组构件里最常见的 `Type Name` | `CR` → **冷冻水管** |

鼠标悬停分组行会列出完整对应关系，例如：

```
EAD（排风管，来源：模型自带「系统类型」）
系统分类：排风
系统类型：EAD-排风管
系统名称（2 种）：EAD 5、EAD 6
```

要新增或改正对照表里的名字，只改 `system-names.js` 的 `SYSTEM_NAMES`，键统一大写即可。
（`CR`、`CS` 这类在不同项目里含义不统一的缩写刻意不硬编码，交给 ①②④ 用模型自己的说法。）

要点：

- **编号永远不参与归属**：`CN 5`/`CN 7`/`CN 15` 是同一个类别 `CN`，只有构件数会累加。
- **缩写里的字母后缀有区分意义**，保留：`CHW-A` 与 `CHW-B` 是两个类别。
- 分组节点悬浮时会列出**归一化前的原始取值**（如 `CN 5、CN 7、CN 15、cn-9`），
  这样既能按缩写收拢，又不会丢失原始系统名。
- 构件自身名称不受影响，叶子上仍显示原始名（如 `圆形风管 CN 15`）。

#### 专业判定规则（第一层怎么来的）

`src/viewer/discipline.js` 里的 `disciplineCode()`，从强到弱依次尝试，先命中先返回：

| 顺序 | 依据 | 例子 |
|---|---|---|
| ① | 模型自带 `专业` / `专业名称` 字段 | `消防` → **消防** |
| ①b | **建筑构件类别 → 一票否决**（墙 / 门 / 窗 / 楼板 / 梁 / 柱 / 幕墙…）→ 建筑（结构构件给结构） | `基本墙 3H防火板墙_150`（类别=墙）→ **建筑**；`门 \| 智能防火门` → **建筑** —— 名字带「防火」也还是墙和门 |
| ② | **消防优先**：中文关键词命中消防词 | `排烟` → **消防**、`火灾报警` → **消防** |
| ③ | **BIM 语义层里的消防**：IFC 实体 / OmniClass 指到消防 | `IfcFireSuppressionTerminal` → **消防** |
| ④ | **系统中文语义**（系统分类 / 系统类型 / 系统名称）按命中词数打分 | `生活给水` → 给排水、`弱电` → 智能化 |
| ⑤ | **BIM 语义层**：IFC 实体 / OmniClass 编码 | `IfcChiller` → 暖通、`23.33` → 暖通 |
| ⑥ | 系统缩写查内置表（66 条，兜底） | `CHW` → 暖通、`XH` → 消防 |
| ⑦ | 兜底词：系统泛词 → 类别强词 → 设备名 → 类别 / 族泛词 | `墙` → 建筑、`板式换热器` → 暖通 |
| ⑧ | **手工命名规则** `系统名_设备名+编号`（见下节） | `智能照明_筒灯001` → **电气** |
| ⑨ | **同类别多数**（整批看，见下） | 同类别 3 条都是给排水 → 第 4 条也归给排水 |
| ⑩ | 都没有 | **其他分类**，不瞎猜 |

> ①b 为什么排在消防优先之前：防火板墙、防火门、防火卷帘、防火窗名字里都带「防火」，
> 若按关键词判就会整批落进「消防」专业（某 31F 模型里 2 堵 `基本墙 3H防火板墙_150` 就是这样），
> 于是「消防 › 墙」——专业与构件对不上。墙就是墙，建筑分隔构件归建筑专业；
> 消防专业管的是消防系统本体（喷淋、消火栓、火灾报警、防排烟、灭火设施）。
> 这一条与设备层 `equipment.js` 的「建筑构件类别一票否决」共用同一张类别表
> （`discipline.js` 的 `buildingCatCode()`），两档视图的归属不会再打架。

**BIM 语义层是什么、依据哪来的**（`ifcDiscipline()` / `omniclassDiscipline()`）：

- **IFC 实体**（IFC4 / ISO 16739-1）。IFC 的建筑设备域本身就是按专业 schema 拆的 ——
  `IfcHvacDomain`（暖通）、`IfcPlumbingFireProtectionDomain`（给排水与消防）、
  `IfcElectricalDomain`（电气）、`IfcBuildingControlsDomain`（楼控）。
  实体名直接说明"这是什么设备"，比中文词可靠：`IfcChiller` 冷水机组、`IfcBoiler` 锅炉、
  `IfcPump` 泵、`IfcValve` 阀门、`IfcFan` 风机、`IfcDuctSegment` 风管段、
  `IfcSanitaryTerminal` 卫生器具、`IfcLightFixture` 灯具、`IfcCableCarrierSegment` 桥架、
  `IfcTransformer` 变压器、`IfcSensor` 传感器、`IfcFireSuppressionTerminal` 喷淋末端。
  读取方式是扫属性里所有含 `ifc` 的键（`导出类型到 IFC`、`IFC 类型`、`ifcType`…），取 `IfcXxx` 实体名。
- **OmniClass Table 23（Products）**。一级类目就是按产品族分的，编码段可以直接当专业判据：
  `23-25` 结构与空间分隔、`23-29` 设施与人身防护（消防 / 安防要按标题拆）、`23-30` 洞口通道、
  `23-31` 给排水、`23-33` 暖通空调、`23-35` 电气与照明、`23-37` 信息与通信。
  模型里带 `OmniClass 编号 / OmniClass 标题` 时直接用（本例 B1 的 `23.30.10.00 Doors`、`23.25.30.11.14.11 Columns`）。

**为什么 IFC/OmniClass 排在「系统语义」之后**：实体只说明"这是什么设备"，系统才说明"它属于哪个专业"。
一台 `IfcPump` 装在冷冻水系统里是暖通的、装在生活给水系统里才是给排水的。
所以顺序是「系统的说法 > 设备的说法 > 缩写的说法」。

两条容易踩的规则：

- **中文语义排在缩写之前**。`系统分类 / 系统类型` 是模型自己写的权威口径，缩写只是各院自定的代号：
  同一个 `NW`，在这个项目里是「空调凝结水 + 坡道雨水」（给排水），在别的项目里可能真是 network。
  所以先看语义，语义判断不出来才用缩写表兜底。
- **混合水系统按排水算**：一个系统里同时出现空调类词（空调 / 冷凝水 / 冷冻水…）和排水类词
  （雨水 / 污水 / 废水 / 排水 / 中水）时，归**给排水** —— 它是把水排走的系统，
  不是制备冷热水的系统。`NW-空调凝结水、坡道雨水` 就是靠这条落到给排水的。
- **`机械设备` 是跨专业的泛类别**：Revit 里板式换热器、冷水机组、水泵、水箱都挂在它下面，
  光看类别定不了专业，所以单独有一张**设备词表**（换热器/冷水机组/空调机组/风机盘管 → 暖通，
  水泵/水箱/水处理 → 给排水，变压器/配电柜 → 电气…），用族与类型名来定。
- **弱词表里不放单字**：早先收过单字「板」（为识别结构板），结果把「板式换热器」认成了结构板；
  现在只收多字词（楼板 / 预制板 / 现浇板 / 框架柱…）。同理不用「柱」而是「框架柱」「构造柱」。
- **同类别多数兜底**（`classifyLeaves`）：属性本身判不出的构件，看**同一类别里已经判对的那批**
  是什么专业，跟着走。三道闸防止乱归：① 泛类别（`机械设备` / `常规模型` / `专用设备`…）不参与；
  ② 该类别已判对的样本 ≥ 3 条；③ 最高专业占比 ≥ 75%。不满足就老实留在「其他分类」。

#### 手工添加的非 BIM 模型：按命名规则归类

现场会往场景里手工补一些非 BIM 模型（筒灯、喷淋头、摄像头…）。它们没有 `extras`，
属性判定必然落到「其他分类」。这类模型唯一可用的线索是名字，所以约定一条命名规则：

```
系统名 _ 设备名 + 编号         例：智能照明_筒灯001、消防_喷淋头012、给排水_地漏03
```

解析在 `manual-name.js`（`parseManualName()`），只做字符串拆解，不判断专业：

| 部分 | 取法 | 例子 |
|---|---|---|
| 分隔符 | 第一个 `_`；兼容全角 `＿`，连续多个下划线算一个 | — |
| 系统名 | 分隔符前；尾部编号不算系统名 | `智能照明1_筒灯001` → 智能照明 |
| 设备名 | 分隔符后、去掉尾部编号；允许内部再有下划线 | `EAD_排风管_003` → 排风管 |
| 编号 | 末尾 1~6 位数字，允许前置 `#` / `-` / `~` / 空格 | `筒灯#001` → 001 |

判定方式（`resolveDiscipline()`）：**系统名按「系统语义」的同一套关键词打分**（`智能照明` → 电气、
`消防` → 消防、`给排水` → 给排水、`智能化` → 智能化），**设备名进设备词表与弱词表兜底**
（`EAD_排风管` 靠「风管」落到暖通）。判定来源记为 `manual`，树上悬浮提示写明
「构件命名规则 · 系统名「智能照明」」。

处理边界（格式不规则 / 认不出时的口径）：

| 情形 | 处理 |
|---|---|
| 属性里有系统字段 | **属性优先**，名字不参与 —— 用户随手起的名不能盖掉模型自带的权威口径 |
| 没有 `_` 分隔符（`筒灯001`） | 不按规则解析，留在「其他分类」，提示「没有「_」分隔符」 |
| 系统名缺失 / 只有编号 / 单字母（`_筒灯001`、`123_筒灯001`、`A_筒灯001`） | 格式不规则 → 留在「其他分类」，提示具体原因 |
| 设备名缺失或只有编号（`智能照明_`、`智能照明_001`） | 同上 |
| 缺编号（`智能照明_筒灯`） | **仍然归类** —— 编号可缺，系统名与设备名不可缺 |
| 系统名认不出专业（`构件甲_未知设备001`） | 留在「其他分类」，且**不建系统分组**——免得「其他分类 > 构件甲」看着像个正经系统 |
| 与「同类别多数」冲突 | 命名规则优先（名字是显式声明），多数推断只用于完全没线索的构件 |

「其他分类」的悬浮提示会直接写进桶原因（例如「没有「_」分隔符」），
`report-unknown.mjs` 也会按原因汇总，方便批量改名或补属性。

### 取景：三个会把模型"裁掉"的坑

1. **`controls.maxDistance` 写死**。V1 里是 `50_000`，而 60 m × 60 m 的楼层需要 99,000 的距离才装得下——
   `fit()` 把相机推远后 `controls.update()` 又按 maxDistance 拽回来，于是永远只显示中间一块。
   现在按模型尺度动态设 `maxDistance = dist × 6`。
2. **只按竖直 FOV 算距离**。两侧面板一开，视口宽高比从 2.4 掉到 1.16，横向就会被裁。
   现在取横竖视场角里较小的那个。
3. **包围球对扁平的楼层太保守**。半径取的是对角线一半（43,000），而楼层真正占的是 30,000 × 30,000，
   结果模型缩成画面中间一小块。现在按 8 个角点的实际投影迭代 3–6 次收紧到铺满 88%–90%，
   同时保证 8 个角点全在画面内（自动化测试直接断言这一点，见 `test/verify-view.mjs`）。

## 压缩用的是 meshopt，不是 Draco

这不是随手换的技术选型，是实测后的唯一可行路径：

| 方案 | 结果 |
|---|---|
| Draco 编码（官方 npm `draco3d`） | **不行**。只有 Node 版 glue，浏览器里 `require('fs')` 直接炸 |
| Draco 编码（three.js 自带 `draco_encoder.js`，asm.js） | **不行**。Chrome 157 里一初始化就 `Target crashed`，换 `TOTAL_MEMORY` 等参数无效 |
| gltf-transform 的 `meshopt()` 封装 | **不行**。内部强制调 `quantize()`，会把 `KHR_materials_volume.thicknessFactor` 按节点缩放改写（0.2 → 0.00024），共用材质还会被克隆出多份 |
| **`reorder()` + `EXT_meshopt_compression` FILTER** | **可行**。顶点保持 Float32、材质与节点变换一字不动，压缩率反而更高（−45.7% vs −29.7%） |

Draco 的**解码器**仍然保留（`public/draco/draco_decoder.js`，asm.js 版），用来读入「源文件本身就被 Draco 压过」的情况——你的 3ds Max 导出基本都属于这种。

**所以输出的扩展名是 `EXT_meshopt_compression`**，不是 `KHR_draco_mesh_compression`。three.js 的 `GLTFLoader` 两者都原生支持，用法没有任何区别（本项目里 `setMeshoptDecoder()` 已接好）。

## 材质与光照：PBR 模型为什么以前会全黑

查看器用的是 glTF 2.0 标准的 **金属-粗糙度（metallic-roughness）PBR**，材质交给 three 的
`MeshStandardMaterial` 渲染。也就是说「PBR 材质」本身是支持的 —— 全黑是另外三件事：

| 现象 | 根因 | 现在的处理 |
|---|---|---|
| 金属 / 抛光件纯黑，非金属正常 | `metalness=1` 的材质几乎没有漫反射，颜色**全部来自环境反射**；早先场景里只有平行光、没有 IBL | 用 three 自带的 `RoomEnvironment` 生成 PMREM 环境贴图，按 `metalness²` 挂到金属与透射玻璃上（电介质不挂，避免灰墙被洗白） |
| 整片发白/发灰、颜色不对 | 旧版 **高光-光泽度** 材质 `KHR_materials_pbrSpecularGlossiness`，three r157 之后已移除支持 | 加载时体检扩展，用 gltf-transform 的 `metalRough()` 就地转成金属-粗糙度，并提示「已把 N 个旧版高光材质转为金属-粗糙度」 |
| 部分构件黑（墙、型钢） | 图元里没有 material 索引时 GLTFLoader 会造「白 + metalness 1 + roughness 1」的默认材质 | 批处理阶段换成灰白素模材质（`FALLBACK`），见 `test/batch-default-mat.mjs` |
| 整模型全黑、材质数值却都正常 | 带 `COLOR_0` 的模型被 GLTFLoader 标成 `vertexColors = true`；批处理把 normalized 顶点属性**反归一化了两次**（`getComponent()` 已 denormalize，外面又除了一次分母），白色 255 → 1/255 | 只取 `getComponent()`，不再除分母；`test/vc-normalized.mjs` 守住（否则量化坐标还会被再缩 32767 倍） |

支持的材质扩展（GLTFLoader r170 实现）：`KHR_materials_clearcoat`、`sheen`、`transmission`、
`volume`、`ior`、`specular`、`iridescence`、`anisotropy`、`dispersion`、`emissive_strength`、
`unlit`、`EXT_materials_bump`。表外的 `KHR_materials_*` 会在加载后提示「材质扩展未支持」，
不静默装没事。

光照参数是拿真实模型（`117_U_B1`）做过 A/B 的：半球光 1.35 / 主光 1.5 / 补光 0.55 / 轮廓光 0.4，
环境贴图只给金属（强度 0.6 × metalness²）。电介质材质的外观与加 IBL 之前**逐像素一致**
（实测均值 228.5，与改动前相同），避免「修好金属、洗白全楼」。

> 自查脚本：`node test/pbr-metal.mjs`（金属不能黑）、`node test/spec-gloss.mjs`（旧材质能转）。

## 已知限制

1. **内存**。208 MB / 748 万顶点的文件，浏览器堆峰值约 2.5 GB。16 GB 内存的机器够用；
   如果你有更夸张的楼层（比如 500 MB+），建议还是走 `bimpack` 的 Node CLI（见上级目录 README）。
2. **压缩率不如 Draco**。浏览器里做不到 Node 版 Draco 的 −69%，FILTER 编码的上限就在这。
   想压得更狠，用 Node CLI 的 `gltf-transform draco`。
3. **文件体积太小时压缩反而变大**（1.2 KB → 1.8 KB），因为多了扩展声明和 bufferView 头。
   小文件建议直接用「下载」拿修过版本的原始文件。
4. **首屏解码时间**。208 MB 约 24–30 秒（软件渲染环境），真实 GPU 环境会更快；
   期间进度卡会显示到了哪一步。

过渡期间要有中间帧（不是瞬移）、再双击同一目标 / 按 `Esc` / 双击空白后必须回到初始视角
（偏差 < 模型尺度的 0.1%），且「适应视图」仍可用并清掉返回点。
同一份测试还管「聚焦后能滚回去」：拉远上限必须 ≥ 全景距离、远裁面必须覆盖整模型，
并用真实滚轮事件验证「拉远后 8 个角点仍在画面内」。

测试用系统装好的 Chrome（`channel: 'chrome'`），不需要额外下载浏览器。
