# BIM Pack Web · GLB 处理与查看

纯前端（浏览器内运行）的 GLB 处理工具：**拖入模型 → 体检 → 压缩 → 3D 预览 → 层级树 → 下载**。
不依赖 Node 服务、不上传文件，所有计算都在本地浏览器完成。

打开的界面就是拖放区——不自动加载任何模型。

---

## 怎么跑

```bash
cd bimpack/web
npm install          # 只需第一次
npm run dev          # → http://localhost:5173
```

构建成静态站点（可丢到任意静态托管：GitHub Pages / OSS / COS / Nginx）：

```bash
npm run build        # 产物在 dist/，用相对路径，放子目录也能跑
npm run preview      # 本地预览构建产物
```

> `dist/` 是纯静态文件，没有任何服务端依赖。但**不能直接双击 index.html**——
> ES module 和 wasm 在 `file://` 下会被浏览器的同源策略拦住，必须走一个静态服务器。

---

## 能干什么

| 能力 | 说明 |
|---|---|
| **直接查看** | 拖入 `.glb` 立刻渲染，不做任何几何改动（只修非法的 `asset.version`） |
| **压缩处理** | reorder + meshopt FILTER 编码，实测 208 MB → 113 MB（−45.7%） |
| **层级树** | 按 BIM 属性合成**规范层级**：专业 → 系统 → 类别 → 类型 → 构件（源文件是平铺的，见下），另可切局部视图，懒加载 + 名称搜索 |
| **BIM 属性** | 点构件看全部 `extras` 用户属性（实测单构件 71 条） |
| **批处理渲染** | 12,209 个独立 Mesh → **29 个 draw call**（按材质分组） |
| **校验闸门** | 压缩后跑 19 项比对，任何一项不过都不会让你下载 |
| **拒绝重复压缩** | 已经压到极限的文件（≤8 字节/顶点）不再让压，按钮直接变「已压缩」 |
| **下载** | 处理后的 `.glb`，或仅修过版本的原始文件 |

### 交互

- 左键拖 = 旋转，右键拖 = 平移，滚轮 = 缩放
- **单击构件 = 只高亮 + 出属性，相机不动**（在模型上点、在树上点都一样）
- **双击构件 = 相机定位过去**（想看清某个构件时用）
- 树上的「▤」是分组、「◆」是构件；点分组名会展开，右侧数字是该组构件数
- 顶栏「层级树 / 属性」按钮、面板右上角 `×`、快捷键 `1` / `2` = 显示或收起面板
- 「适应视图」（快捷键 `F`）= 回到能看全整个模型的角度；「俯视」= 正上方看平面；「网格」= 地面参考网格
- 搜索框输名称 = 全树过滤，点结果直接选中
- `Esc` = 取消选中

> 面板收起/展开、窗口缩放时，只要**你没手动转过视角**，相机就会自动重新取景，
> 保证模型始终完整显示（这是 V1 里"模型装不下"的根因之一，见下一节）。

### 为什么压过的文件不让再压

不是保守，是数学。Draco / meshopt 的量化把坐标存成 16 bit 整型，浏览器端的
meshopt FILTER **不做量化**、只做 delta + 熵编码，读进来坐标又变回 float32。
所以「量化解回浮点再压一次」必然膨胀 —— 实测一份 63.63 MB 的 Draco 产物被压成了 **115.34 MB**。

判据不是「有没有 Draco 扩展」：**3ds Max 的原始导出本身就带 Draco**，但用的是低压缩设置
（25.46 字节/顶点），重压能到 4.5，这正是主流程。所以看的是每顶点字节数：

| 文件 | 字节/顶点 | 按此按钮 |
|---|---|---|
| 3ds Max 原始导出 | 25.46 | ✅ 可压 |
| 本工具 meshopt 产物 | ≈11.3 | ⛔ 已压缩（同算法无收益） |
| Draco edgebreaker 产物 | 4.54 | ⛔ 已压缩（已到极限） |

低于 **8 字节/顶点** 就判定为「压够了」。要更小只能回到原始导出，用**本地 Draco 工具**
重压（那个工具在本机 `local-tools/draco-tool/`，**不在本仓库**），它做量化，
实测 208 MB → 63 MB（−69.6%），比浏览器版多压一半。

### 为什么有的模型会报 `Cannot read properties of null (reading 'length')`

这不是模型的几何坏了，是导出的 JSON 里有**规范不允许的 null**。最常见三处：

- 图元上的 `"targets": null`（形变目标）
- 节点 / mesh 上的 `"weights": null`（形变权重）
- mesh 里没有 `primitives`

three.js 的 `GLTFLoader` 在这些地方用 `!== undefined` 判空，null 会被当成「有值」，
接着直接 `null.length` —— 报错就长这样，且完全看不出是哪个字段。

所以进解析器之前会做一次字节级清洗（`core/glb.js` 的 `prepareGLB`）：

1. 把 `extras` 之外的 null **删掉**（删掉 = 回落到规范默认值；`extras` 是 BIM 属性，里面的 null 原样保留）
2. 引用型数组（场景根节点、children、joints、primitives、targets）里的 null 元素剔除
   —— 注意只动这类「纯引用列表」，像 `nodes` / `meshes` / `accessors` 这种按**下标**被引用的数组绝不能删元素
3. 没有 `primitives` 的 mesh 补成 `[]`，退化成一个空 Group 被批处理跳过 —— 一个坏图元不该让整层楼打不开

回归测试：`node test/sanitize.mjs`（9 项断言，含「extras 里的 null 必须保留」）。

### 为什么层级树是"合成"的

3ds Max 的 glTF 导出器把这层信息丢掉了：本例 208 MB 文件里 **12,244 个节点全在根上、
零子节点、最大深度 0**。照原样铺就是一条一万多行的平列表——既看不懂也没法用。

所以按 `extras` 里的 BIM 属性合成层级。**主线只有一套**：专业 → 系统 → 类别 → 类型 → 构件；
其余分组是同一批构件的**局部视图**（单轴展开），不是并行的第二棵树 ——
构件不会在多棵树里重复出现，分组计数之和永远等于构件总数。

#### 为什么用「专业」当总层

模型里其实有两套**正交**的轴：

- **构件分类轴**：类别 → 族 → 类型 → 构件（IFC 的 `IfcTypeObject` 体系，即 Revit 的 Category / Family / Type）
- **系统轴**：系统 → 构件（IFC 的 `IfcDistributionSystem` + `IfcRelAssignsToGroup`）

一根排烟风管，既「是一种风管」，又「属于某个排烟系统」。要合成一棵树，必须选一条当主干、
把另一条降级。按机电出图与验收的惯用口径，顺序是**先分专业、再分系统、最后才是构件类别**，
于是主干定为五级：

| 层级 | 取值来源 | 例子 |
|---|---|---|
| ① 专业 | 由系统字段 / 类别 / 族推导（`src/viewer/discipline.js`） | 暖通空调 / 给排水 / 消防 / 电气 / 智能化 / 燃气 / 建筑 / 结构 |
| ② 系统 | `系统缩写` 优先，没有才解析 `系统名称` | `PY` `CHW` `SP` `AL` |
| ③ 类别 | `Category Name` | 风管 / 管道 / 电缆桥架 |
| ④ 类型 | `Type Name` | 镀锌铁皮 / 无缝钢管 |
| ⑤ 构件 | 网格实例 | `排烟风管 PY 5` |

**依据**（口径来源，不是自创）：

- GB/T 51269-2017《建筑信息模型分类和编码标准》：按专业—系统—构件类型分层编码
- GB/T 51301-2018《建筑信息模型设计交付标准》：模型按专业与系统组织，系统应可追溯
- IFC4（ISO 16739-1）`IfcDistributionSystem.PredefinedType`：AIRCONDITIONING / VENTILATION /
  DOMESTICCOLDWATER / SANITARY / FIREPROTECTION / ELECTRICAL / COMMUNICATIONS
- 各专业验收规范的划分：GB 50242（给排水及采暖）、GB 50243（通风与空调）、GB 50303（建筑电气）、
  GB 50974（消防给水及消火栓）、GB 51251（防烟排烟）、GB 50116（火灾自动报警）、
  GB 51309（消防应急照明）、GB 55037（建筑防火通用规范）

#### 原来的多套层级怎么合并

| 原分组 | 合并后的位置 |
|---|---|
| 类别 → 类型 | 主干第 ③④ 层 |
| 系统（缩写） → 类别 | 主干第 ②③ 层（上方新增 ① 专业） |
| 系统（缩写） → 类别 → 类型 | 主干第 ②③④ 层 |
| 族 → 类型 | **不占主干**：`族` 与 `类型` 语义重叠（Family 是 Type 的容器），降为可选第 ④ 层（`专业→系统→类别→族→类型`）；其余场合当构件属性看 |
| 标高 → 类别 | **不进主干**：楼层是空间维度，与系统维度正交。一根立管跨 31 层，塞进树里只能二选一（重复 31 次，或丢掉楼层信息）。保留为局部视图 |
| 原始结构 | 兜底视图：源文件真有层级时才用得上（平的源文件会退化成平列表） |

下拉框按 `规范层级（主线）` / `局部视图` 分成两组，避免误以为是两套并行的树。

**空层折叠**：整层只有一个取值时自动折叠 —— 建筑结构模型没有系统字段，就不会多出一层全是
`(未分类)` 的假层级；单个构件缺系统 / 族时也不给它造空节点，直接挂到上一级（深度按实际经过的层数算）。

#### 归并冲突与特殊处理

| 冲突 | 处理 | 依据 |
|---|---|---|
| 排烟风管：设备是「风管」（暖通），系统是「排烟」（消防） | **消防优先** —— 命中排烟 / 防烟 / 喷淋 / 消火栓 / 火警等词一律归消防，不拆散进暖通或给排水 | GB 55037、GB 51251、GB 50974 要求消防独立成体系、单独验收 |
| 同类别的构件落在两个专业（「风管」在暖通与消防下各有一份） | **允许**：合并粒度是「专业 + 系统」，不是类别。两份互不干扰，叶子不重复 | — |
| 缩写跨项目含义不一（`NW` 在 A 院是凝结水、B 院是网络；`CR` 可能是冷媒或冷却水回水） | 中文语义优先、缩写只作兜底；有歧义的缩写出表（见下）；仍判断不出就用组内最常见类型名，悬浮提示写明来源 | — |
| 消防是否单列存在两种口径（有的院把消防水并入给排水） | `POLICY.fireFirst = false` 时按**实体专业**归并：排烟 → 暖通、喷淋 / 消火栓 → 给排水、火灾报警 → 电气 | 可配置，默认单列 |
| 构件无任何系统字段（建筑 / 结构） | 落到「建筑」「结构」专业；既无系统也无类别 → 「(未分类)」，排在最后 | — |
| 多系统值（`CR 30,CR 18`） | 只取第一个作主系统，避免一个构件在多系统下被重复计数 | — |
| 族与类型重名 / 族跨类别 | 族不进主干（只在可选的第 ④ 层出现），避免「族」和「类别」两套近似语义打架 | — |
| 标高 | 不进主干（见上表），当前用局部视图看，后续计划做成筛选器 | — |


#### 系统归类规则：缩写定类别，编号不参与

机电模型的「系统名称」写法五花八门（`CN 5`、`CN-7`、`cn-9`、`CWP 3`、`CR 30,CR 18`…），
直接用原值分组会把同一个系统拆成一堆平行分组。规则统一为
**「系统缩写 = 类别，缩写后的编号一律忽略」**，对任何模型都用同一套解析（`systemAbbr()`）：

| 步骤 | 处理 | 例子 |
|---|---|---|
| 1 | 多系统值只取**第一个**系统条目（按 `, ， ; ； / 、 \| +` 切分） | `CR 30,CR 18` → `CR 30` → **CR** |
| 2 | 去掉括号注释 | `CN 5(备用)` → **CN** |
| 3 | 取开头字母段（字母间允许 `- _ .` 连接），遇数字/空白/中文即止 | `CN 5` `CN-5` `CN_05` `CN5` `cn 9` → 都是 **CN**；`CHW-B 12` → **CHW-B** |
| 4 | 统一大写、压缩空白 | `cwp 3` → **CWP** |
| 5 | 不以字母开头时，剔除结尾的编号段，其余保留 | `生活给水 JL 3` → **生活给水 JL** |
| 6 | 纯数字/空值没有分类意义 → 归「未分类」 | `12 34` → **（未分类）** |

**分类键优先用模型自带字段**：先取 `系统缩写`（如 `EAD`），没有才解析 `系统名称`（`EAD 5` → `EAD`）。
两者都不看编号，缩写后的数字一律不参与归属。

**缩写后面显示中文系统名**，按四级优先级取，前一级拿不到才退下一级：

| 优先级 | 来源 | 例子 |
|---|---|---|
| ① | 模型自带 `系统类型`（去掉缩写前缀） | `EAD-排风管` → **排风管** |
| ② | 模型自带 `系统分类` | `排风` → **排风** |
| ③ | 内置对照表 `src/viewer/system-names.js` | `CN` → **冷凝水**、`CWP` → **冷却水泵** |
| ④ | 该组构件里最常见的 `Type Name` | `CR` → **冷冻水管** |

鼠标悬停分组行会列出完整对应关系，例如：

```
EAD（排风管，来源：模型自带「系统类型」）
系统分类：排风
系统类型：EAD-排风管
系统名称（2 种）：EAD 5、EAD 6
```

要新增或改正对照表里的名字，只改 `system-names.js` 的 `SYSTEM_NAMES`，键统一大写即可。
（`CR`、`CS` 这类在不同项目里含义不统一的缩写刻意不硬编码，交给 ①②④ 用模型自己的说法。）

要点：

- **编号永远不参与归属**：`CN 5`/`CN 7`/`CN 15` 是同一个类别 `CN`，只有构件数会累加。
- **缩写里的字母后缀有区分意义**，保留：`CHW-A` 与 `CHW-B` 是两个类别。
- 分组节点悬浮时会列出**归一化前的原始取值**（如 `CN 5、CN 7、CN 15、cn-9`），
  这样既能按缩写收拢，又不会丢失原始系统名。
- 构件自身名称不受影响，叶子上仍显示原始名（如 `圆形风管 CN 15`）。

#### 专业判定规则（第一层怎么来的）

`src/viewer/discipline.js` 里的 `disciplineCode()`，从强到弱依次尝试，先命中先返回：

| 顺序 | 依据 | 例子 |
|---|---|---|
| ① | 模型自带 `专业` / `专业名称` 字段 | `消防` → **消防** |
| ② | **消防优先**：系统字段或类别含消防词 | `排烟` → **消防**、`火灾报警` → **消防** |
| ③ | **系统中文语义**（系统分类 / 系统类型 / 系统名称）按命中词数打分 | `生活给水` → 给排水、`弱电` → 智能化 |
| ④ | 系统缩写查内置表（66 条，兜底） | `CHW` → 暖通、`XH` → 消防、`AL` → 电气 |
| ⑤ | 兜底：系统名泛词 → 类别强词 → **设备名** → 类别 / 族泛词 | `墙` → 建筑、`结构框架` → 结构、`板式换热器` → 暖通 |
| ⑥ | 都没有 | **(未分类)**，不瞎猜 |

两条容易踩的规则：

- **中文语义排在缩写之前**。`系统分类 / 系统类型` 是模型自己写的权威口径，缩写只是各院自定的代号：
  同一个 `NW`，在这个项目里是「空调凝结水 + 坡道雨水」（给排水），在别的项目里可能真是 network。
  所以先看语义，语义判断不出来才用缩写表兜底。
- **混合水系统按排水算**：一个系统里同时出现空调类词（空调 / 冷凝水 / 冷冻水…）和排水类词
  （雨水 / 污水 / 废水 / 排水 / 中水）时，归**给排水** —— 它是把水排走的系统，
  不是制备冷热水的系统。`NW-空调凝结水、坡道雨水` 就是靠这条落到给排水的。
- **`机械设备` 是跨专业的泛类别**：Revit 里板式换热器、冷水机组、水泵、水箱都挂在它下面，
  光看类别定不了专业，所以单独有一张**设备词表**（换热器/冷水机组/空调机组/风机盘管 → 暖通，
  水泵/水箱/水处理 → 给排水，变压器/配电柜 → 电气…），用族与类型名来定。
- **弱词表里不放单字**：早先收过单字「板」（为识别结构板），结果把「板式换热器」认成了结构板；
  现在只收多字词（楼板 / 预制板 / 现浇板 / 框架柱…）。同理不用「柱」而是「框架柱」「构造柱」。

缩写表只收**含义稳定**的（`CHW` `XH` `SP` `AL` `JL` …）。`NW` `W` `FS` `TR` `HW` `HWS` `HWR`
`QT` `SSP` `FFS` `WSF` 这些有歧义的已经删掉了——早先 `NW` 按“network”理解，
结果把「空调凝结水、坡道雨水」整支误判成了智能化。`CR`/`CS`/`F` 这类各院口径不一的也同样不收。
要按某个项目的口径固化，改 `ABBR_DISCIPLINE` 这一张表即可。

对应实现：`src/viewer/tree.js`（`GROUP_MODES` / `systemKey`）、`src/viewer/discipline.js`（专业归并）、
`src/viewer/system-key.js`（缩写提取）；
回归测试：`test/system-abbr.mjs`（30+ 句型）、`test/discipline.mjs`（专业判定 + 消防优先策略）、
`test/tree-system.mjs`、`test/tree-unified.mjs`（真实加载后校验五级主干、不重不漏）。


### 取景：三个会把模型"裁掉"的坑

1. **`controls.maxDistance` 写死**。V1 里是 `50_000`，而 60 m × 60 m 的楼层需要 99,000 的距离才装得下——
   `fit()` 把相机推远后 `controls.update()` 又按 maxDistance 拽回来，于是永远只显示中间一块。
   现在按模型尺度动态设 `maxDistance = dist × 6`。
2. **只按竖直 FOV 算距离**。两侧面板一开，视口宽高比从 2.4 掉到 1.16，横向就会被裁。
   现在取横竖视场角里较小的那个。
3. **包围球对扁平的楼层太保守**。半径取的是对角线一半（43,000），而楼层真正占的是 30,000 × 30,000，
   结果模型缩成画面中间一小块。现在按 8 个角点的实际投影迭代 3–6 次收紧到铺满 88%–90%，
   同时保证 8 个角点全在画面内（自动化测试直接断言这一点，见 `test/verify-view.mjs`）。

## 压缩用的是 meshopt，不是 Draco

这不是随手换的技术选型，是实测后的唯一可行路径：

| 方案 | 结果 |
|---|---|
| Draco 编码（官方 npm `draco3d`） | **不行**。只有 Node 版 glue，浏览器里 `require('fs')` 直接炸 |
| Draco 编码（three.js 自带 `draco_encoder.js`，asm.js） | **不行**。Chrome 157 里一初始化就 `Target crashed`，换 `TOTAL_MEMORY` 等参数无效 |
| gltf-transform 的 `meshopt()` 封装 | **不行**。内部强制调 `quantize()`，会把 `KHR_materials_volume.thicknessFactor` 按节点缩放改写（0.2 → 0.00024），共用材质还会被克隆出多份 |
| **`reorder()` + `EXT_meshopt_compression` FILTER** | **可行**。顶点保持 Float32、材质与节点变换一字不动，压缩率反而更高（−45.7% vs −29.7%） |

Draco 的**解码器**仍然保留（`public/draco/draco_decoder.js`，asm.js 版），用来读入「源文件本身就被 Draco 压过」的情况——你的 3ds Max 导出基本都属于这种。

**所以输出的扩展名是 `EXT_meshopt_compression`**，不是 `KHR_draco_mesh_compression`。three.js 的 `GLTFLoader` 两者都原生支持，用法没有任何区别（本项目里 `setMeshoptDecoder()` 已接好）。

## 已知限制

1. **内存**。208 MB / 748 万顶点的文件，浏览器堆峰值约 2.5 GB。16 GB 内存的机器够用；
   如果你有更夸张的楼层（比如 500 MB+），建议还是走 `bimpack` 的 Node CLI（见上级目录 README）。
2. **压缩率不如 Draco**。浏览器里做不到 Node 版 Draco 的 −69%，FILTER 编码的上限就在这。
   想压得更狠，用 Node CLI 的 `gltf-transform draco`。
3. **文件体积太小时压缩反而变大**（1.2 KB → 1.8 KB），因为多了扩展声明和 bufferView 头。
   小文件建议直接用「下载」拿修过版本的原始文件。
4. **首屏解码时间**。208 MB 约 24–30 秒（软件渲染环境），真实 GPU 环境会更快；
   期间进度卡会显示到了哪一步。

## 与 Node CLI（上级目录）的分工

| | Web 版（本目录） | Node CLI（`../`） |
|---|---|---|
| 使用方式 | 浏览器拖文件，零安装 | 命令行 / 批处理 |
| 压缩算法 | meshopt FILTER | Draco（edgebreaker） |
| 压缩率 | −45.7% | −69.6% |
| 属性校验 | 19 项（JSON + 世界坐标几何） | 19 项（含逐顶点最近邻偏差） |
| 适合 | 单层快速处理、现场看模型、给非技术同事用 | 批量出交付物、极致压缩、CI 集成 |

两者产物的 `userData` / `extras` 都是零丢失，可以互相替换。
